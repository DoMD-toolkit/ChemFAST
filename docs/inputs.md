# Input reference

Use this page to identify the files passed between [workflow](workflow.md) stages.
To write a configuration, use the [Reaction-DSL reference](reaction-dsl.md), which
defines the fields, reaction semantics and structured-filler mappings. The
[usage guide](usage.md) shows how to generate and consume these files.

| File | Provided or generated by | Format and purpose |
|---|---|---|
| `system.json` | User | JSON: reactants, reaction rules and ChemFAST input options |
| Filler reference | User | PDB: reference geometry, with mappings declared in the DSL |
| `initial.xml` | CG preparation | PyGAMD XML: initial particles, coordinates and connectivity |
| `cg_ff_parameters.json` | CG parameterization | JSON: bonded and non-bonded CG parameters |
| `run_pygamd_polymerization.py` | CG preparation | Python: simulation and reaction-execution protocol |
| `reaction_final.xml` | CG simulation | PyGAMD XML: final configuration consumed by FG |
| `reaction_path.txt` | CG simulation | Text: one ordered reaction tuple per line, consumed by FG |
| `atomistic.sdf` | FG | SDF: AA topology, coordinates and export metadata |
| `system.gro`, `system.top`, `*.itp` | FF/export | GROMACS coordinates and topology files |

Filenames are configurable. Keep the DSL, final XML and ReactionPath from the same
construction run together.

## Configuration

The JSON document combines the [reaction-language fields](reaction-dsl.md#document-structure)
with the following ChemFAST options:

| Field | Purpose and format |
|---|---|
| `cg_topology_file` | Path to the final PyGAMD XML configuration for FG |
| `reaction_path_file` | Path to the matching tuple-per-line ReactionPath text file for FG |
| `box_tensor` | Optional initial CG box lengths `[Lx, Ly, Lz]` in nm for an orthorhombic box |

For `build_pygamd_protocol`, omitting `box_tensor` generates a cubic box from the
total system mass and `mass_density`, whose default is **0.9 g/cm³**. Set a box
explicitly in the configuration dictionary, or supply a density to the function:

```python
# Explicit initial box (nm):
config["box_tensor"] = [20.0, 20.0, 20.0]
protocol = build_pygamd_protocol(config, output_dir="cg")

# Alternatively, omit box_tensor and set the initial density:
config.pop("box_tensor", None)
protocol = build_pygamd_protocol(config, output_dir="cg", mass_density=0.6)
```

Import this function from `chemfast.cg.pipeline`. An explicit box takes precedence
over density. **During FG, the box is read from the final XML; `box_tensor` in the
JSON is ignored.**

The two FG files need not exist during CG preparation. After simulation, pass
their actual paths in a copy of the configuration dictionary; the JSON need not
be rewritten. For file-based `build_pygamd_protocol`, relative reference paths
resolve against the JSON directory. Direct FG `parse_config` calls resolve them
against `work_dir`; pass the JSON parent directory or use absolute paths.

(reactionpath)=
## Reaction files and correspondence

The PyGAMD runner writes `reaction_path.txt` as one Python tuple literal per line:

```text
('A-B1', 0, 32)
('B1-A', 32, 1)
```

The first value identifies the reaction; remaining values are zero-based CG node
IDs in reactant-slot order. For the first line, node `0` occupies the A slot and
node `32` the B1 slot. Lines preserve accepted-event order. Do not sort them or
renumber particles independently of the XML. See [Workflow](workflow.md) for why
the final connectivity cannot always replace this record.

The Python reaction engine also provides `ReactionPath.to_dict()`, a richer event
representation containing reaction IDs, steps, participating nodes and sampling
metadata. Coupled type changes have separate events linked to the primary event.
That representation is not the tuple-per-line input read directly by the current
FG parser; do not substitute a JSON event export for `reaction_path.txt`.

(cg-xml)=
## CG configuration: XML

The initial and final files use a PyGAMD/GALAMOST-style XML configuration. The
final file contains the connectivity built during polymerization. Important
sections are:

| Section | Contents |
|---|---|
| `configuration` | Particle count, dimension and simulation step |
| `box` | Box lengths and, where present, tilt factors; use the box convention supported by your workflow |
| `position` | One `x y z` position per particle, in nm in this pipeline |
| `type` | One CG type name per particle, consistent with the DSL and parameter JSON |
| `bond` | Rows such as `A-B1 0 32`: bond type and two particle indices |
| `angle` | Angle type followed by three particle indices; the middle index is the vertex |
| `mass`, `charge`, `image`, `body` | Particle masses, charges, periodic images and rigid-body membership; `body = -1` denotes no rigid body |
| Additional generated sections | Mapping and reaction-state data used by the generated protocol; retain them |

Particle indices refer to row order in the per-particle sections, starting at
zero. XML stores actual particles and connections; the parameter JSON below stores
the force-field terms applied to their types. Both are needed to run the CG
simulation. For fields outside this workflow, consult the engine's XML reference.

(cg-ff-parameters)=
## CG force-field parameters: JSON

`get_cgff_parameters` writes this file. `cg_ff_parameters.json` and the examples'
`cg_parameters.json` use the same schema: the filename is selected by `output`.
Pass the matching file as the parameter argument to the generated runner.

The two top-level objects are `bonded` and `nonbonded`. This excerpt shows one
bond, one angle and one particle type from the supplied example; it is not a
complete runnable parameter set:

```json
{
  "bonded": {
    "A-B1": {
      "ff_type": "CG", "itype": "BOND", "indices": [],
      "params": {"k": 1100.0, "r0": 1.22, "ftype": 1},
      "name": "A-B1", "ff_atom_types": ["A", "B1"]
    },
    "B1-A-B1": {
      "ff_type": "CG", "itype": "ANGLE", "indices": [],
      "params": {"k": 25.0, "r0": 99.8, "ftype": 1},
      "name": "B1-A-B1", "ff_atom_types": ["B1", "A", "B1"]
    }
  },
  "nonbonded": {
    "A": {
      "ff_type": "CG", "ff_atom_type": "A", "bond_type": "",
      "ptype": "A", "params": {"epsilon": 0.663, "sigma": 1.251},
      "element": null, "mass": 1.0, "charge": 0.0,
      "hsp": [19.765, 11.178, 8.281]
    }
  }
}
```

Download the {download}`full supplied parameter example <_static/formats/cg_ff_parameters.example.json>`:
four particle types (A, B1, B2, C), six bond entries and nine angle entries. It
belongs to a different composition from the two-type DSL in the language reference; generate a fresh
parameter file from your own DSL instead of using this download interchangeably.

### Bonded terms

| Field | Meaning |
|---|---|
| Dictionary key / `name` | Interaction-type name used to associate parameters with CG connections |
| `ff_type` | Parameter family, `CG` |
| `itype` | `BOND` or `ANGLE` for the current generated PyGAMD runner |
| `ff_atom_types` | Ordered CG types; the second type is the angle vertex |
| `indices` | Empty for this type-level parameter table; actual particle indices are in the XML |
| `params.ftype` | Potential-function code; `1` selects the supported harmonic form |
| `params.k` | Harmonic stiffness: CG energy/nm² for bonds, CG energy/rad² for angles |
| `params.r0` | Equilibrium bond length in nm for `BOND`; equilibrium angle in degrees for `ANGLE` |

Thus `r0: 1.22` means a 1.22 nm bond, whereas `r0: 99.8` means a 99.8-degree
angle. PyGAMD's harmonic-angle setter accepts degrees and converts internally to
radians; do not convert the JSON value again. See the
[engine's angle convention](https://pygamd-v1.readthedocs.io/en/latest/cuda/cu-forcefield-bonded-angle.html).

The generator uses conformational sampling to estimate equilibrium geometry;
the default stiffnesses are prescribed (`bond_k=1100`, `angle_k=25`), not inferred
chemical reaction rates. Forward/reverse bond names can both occur, and the runner
registers aliases from `ff_atom_types`; do not independently rename one side of a
matching XML/JSON pair. Optional dihedral generation elsewhere in the library
does not imply support in this runner, which currently accepts only harmonic
bonds and angles.

### Non-bonded terms

| Field | Meaning |
|---|---|
| Dictionary key / `ff_atom_type` | CG particle type, e.g. A; must cover the types used by the configuration |
| `params.sigma` | LJ size parameter in nm |
| `params.epsilon` | LJ well depth in the chosen CG energy scale |
| `hsp` | Predicted `[dispersion, polar, hydrogen-bonding]` components in MPa½ |
| `mass`, `charge` | Serialized particle-record values; `1.0` and `0.0` here are CG defaults, not the monomer's molecular mass or an AA charge prediction |
| `ptype`, `bond_type`, `element`, `ff_type` | Shared parameter-record metadata; `ptype: "A"` is a particle-kind flag, not reactant A |

For **multi-atom reactants**, including multi-atom ions such as TFSI⁻, the
current generator predicts HSP components and sets `epsilon` to their squared
magnitude divided by the largest squared magnitude among the included
**multi-atom** types, rounded to three decimals. The largest such type has
`epsilon = 1`. **Only monatomic beads** (for example `[Li+]` or `[Zn+2]`) skip
HSP prediction and are excluded from this normalization. A monatomic bead uses
twice the element's RDKit van der Waals radius (converted to nm) for its default
`sigma` and the **median of the normalized multi-atom epsilon values** for its
default `epsilon`; its serialized `hsp` is `null`. Explicit per-reactant `sigma`
and `epsilon` values override these defaults where supported. An all-monatomic
system without an epsilon reference needs explicit ion parameters.

These are approximate, relative **construction** parameters, not automatically
kJ/mol values or validated LJ ion parameters. The elemental vdW radius is not a
charge- and coordination-specific ionic radius; in a conventional LJ potential,
the energy minimum lies at `2^(1/6) × sigma`. Changing the included multi-atom
types can change the HSP normalization. The SPE examples' neutral-default CG
`mass`/`charge` records do not imply physical lithium or TFSI masses/charges or
explicit electrostatics.

The runner uses arithmetic mixing for `sigma` and geometric mixing for `epsilon`:
`sigma_ij = (sigma_i + sigma_j) / 2`,
`epsilon_ij = sqrt(epsilon_i * epsilon_j)`.
It reads these LJ coefficients directly rather than recalculating them from `hsp`.
Editing `hsp` alone therefore does not change its forces. The runner takes particle
masses and charges from the XML, not these JSON metadata fields, and the shown
non-bonded force is LJ-only. Rigid filler/site records, including the SPE C/CL records, may use an
empirical mean bead size and `epsilon = 1` rather than HSP predictions; see the [HSP scope](workflow.md).

(files-and-units)=
## AA files and units

| Object/file | Convention and use |
|---|---|
| FG internal coordinates and box | Å; CG input lengths are converted from nm |
| `atomistic.sdf` | Explicit AA atoms, bonds and coordinates in Å, plus `RES_NAMES`, `RES_NUMS` and `BOX_TENSOR` metadata used by export |
| `system.gro` | Coordinates and box in nm, with residue and atom labels; not a complete force-field description |
| `system.top` | System topology, included parameter files and molecule counts |
| Molecule `.itp` and `atomtypes.itp` | Molecular connectivity/parameters and shared atom-type definitions |
| `mass_density` | g cm⁻³ |
| AA LJ parameters | `sigma` in nm and `epsilon` in kJ mol⁻¹ |
| Corrected AA `ff.charges` | Elementary charge units |
| CG temperature/time settings | Follow the chosen CG units; `temperature=1.0` does not mean 1 K |
